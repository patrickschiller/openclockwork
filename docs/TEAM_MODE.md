# Team mode

Team mode is OpenClockwork's time-and-attendance workflow for organisations with
employees, managers, and HR administrators. It combines working-time capture,
employee schedules and accounts, leave and correction requests, project work,
reports, and optional shared tablet terminals.

**Existing installations remain in Team mode when upgrading to 2.0.0.** No
employee, manager, kiosk, or approval setup has to be replaced by Solo. Choose
[Solo mode](SOLO_MODE.md) for a genuinely one-person workflow, or read
[Operating modes](OPERATING_MODES.md) before deciding.

## Install and bootstrap

Follow the [production installation guide](../README.md#production-installation-step-by-step).
For this release, use the `v2.0.1` source tag and set
`OPENCLOCKWORK_VERSION=2.0.1` in the private `.env.prod` file. Configure all
required independent secrets, browser origins, the installation's IANA working
timezone (`TZ`), stable volume names, and TLS before using real personal data.

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod pull
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
```

On a new, empty installation, create the first administrator:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec api node --import tsx prisma/create-admin.ts
```

Keep the interactive terminal; do not add `-T`. Explicitly select **Team** at the
mode prompt, whose interactive default is Solo. Enter the administrator's
personnel number, name, email, time model, weekly hours, annual leave, start date,
and optional holiday calendar. Displayed defaults are suggestions, not an
employment policy. The initial password is generated and displayed once; store
it privately and replace it after signing in.

The command refuses to run once any employee exists. Production starts without
demo users or shared passwords. For an existing installation use
[UPGRADING.md](../UPGRADING.md), not a new bootstrap.

For unattended provisioning, `--mode Team` requires `--personal-no`,
`--first-name`, `--last-name`, and `--email`; contract options are available as
well. Inspect the exact options safely with:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec -T api node --import tsx prisma/create-admin.ts --help
```

Existing scripted invocations without `--mode` continue to select Team.
Argument-based invocations do not also prompt for missing fields. Passwords are
generated by the command, not supplied as a command-line option.

## Roles and responsibilities

| Role             | Typical responsibility                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------- |
| Employee         | Own bookings, calendar, time accounts, requests, and substitute tasks                              |
| Manager          | Team request decisions, correction feedback, and authorised project reporting                      |
| HR administrator | Employee records, schedules, allowances, final workflow steps, terminals, and working-time reports |
| Paired kiosk     | Display a rotating QR challenge; never act as an employee or HR user                               |

Assign the actual manager relationships and roles in employee administration.
Being one person with an administrator account does not automatically turn a
Team installation into Solo. Team uses employee workflows until an explicit mode
switch succeeds.

## Configure the organisation

1. **Verify the first administrator.** Review their employee master data and
   change the initial password. Settings provides a current-password-verified
   self-service change for the signed-in administrator; a new password there
   requires at least 12 characters and invalidates existing sessions. HR also
   has the existing employee password-reset workflow.
2. **Create work schedules.** Choose working days, permitted frames, core-time
   windows, and any automatic break rules. Assign schedules to employees or
   bulk-assign by time model.
3. **Create employees and reporting relationships.** Enter start dates, weekly
   hours, roles, managers, holiday calendars, and actual leave entitlements.
   Employee creation is administrator-managed; email invitation/onboarding is
   not part of 2.0.1.
4. **Review accounts.** Configure opening time balances, annual leave,
   carry-over, expiry, and reasoned adjustments as applicable. Check calculations
   against representative contractual cases before operational use.
5. **Create projects and orders.** Set planned hours, assign eligible employees,
   and add service orders when required for allocation.
6. **Configure optional terminals.** Pair a device and set geofencing only if
   it is needed and justified. Direct PWA booking does not require a terminal.
7. **Run a pilot.** Test bookings, requests, manager/HR decisions, reports,
   backups, restore, and the chosen mobile devices with non-sensitive data.

Language and country rules are separate. German and English UI are selectable
at login and in the application. New employee records have no assumed regional
calendar or annual leave entitlement; new schedules have no automatic break
deduction. German regional calendars are optional presets, and custom holiday
dates can cover other regions or company closures. Maintain coverage for every
year you use.

Day boundaries and schedule calculations use one installation working timezone.
A terminal's displayed timezone is independent and does not change employee
accounting. Multiple concurrent employee working timezones are not implemented.
Treat changing `TZ` after work has been recorded as a migration decision, not a
cosmetic preference.

## Employee workday

An employee can clock in/out in the PWA, optionally select GPS and an assigned
active project, and add a customer-facing activity description. Active service
orders become the required booking level for projects that use them. Employees
can review completed entries, adjust their allocation, split work, and use the
supported retroactive-range assignment workflow.

The dashboard shows the employee's current booking, time and leave accounts,
open requests, and applicable core-time information. Calendar and absence views
cover vacation, home office, special leave, sickness, training, and flextime.
Half-day leave and live balance previews help the employee review a request
before submitting it.

If HR explicitly enables direct daily-target booking for an employee, the
employee can create a completed daily-target block instead of a live timer.
Schedule, date, holiday, absence, overlap, frame, and break checks still apply;
this shortcut is not permission to bypass those rules.

The PWA is online-first. Confirm server responses before treating a booking or
request as saved. An offline device is not a second independent time clock, and
disconnection does not stop an already running server timer.

## Requests and approvals

Team mode models explicit workflow states. Depending on the request and
configuration, the path includes:

```text
Employee submits
  → substitute confirmation, when required
  → manager decision
  → HR confirmation, when required
  → approved
```

Managers and HR can approve, reject, return for correction, and use supported
bulk actions. Employees can cancel requests and review workflow history.
Out-of-frame work and time corrections follow the applicable Team rules rather
than Solo's direct owner-correction workflow. Supported requests can include
attachments stored locally or in configured Azure Blob Storage.

Do not assume a request is final merely because one approver accepted it.
Inspect the current state and remaining workflow steps. Historical Solo entries
preserve their original approval mode when the installation later becomes Team;
they do not acquire a new retrospective manager-approval requirement.

## Tablet terminals

HR can configure an ordinary tablet as a branded clock display with an internal
name, visible location, custom message, optional logo, timezone, and optional
GPS geofence. Pair it once with a short-lived code. An employee scans the
rotating QR challenge from their authenticated phone and explicitly chooses
clock-in or clock-out.

The kiosk has its own least-privilege credentials, not an employee login. Pairing
can be revoked or replaced. QR challenges expire and have replay protection.
When a terminal requires location, the server checks a fresh position, accuracy,
and radius; terminals can also run entirely without GPS.

Use a trusted HTTPS origin for camera and geolocation on mobile devices. Follow
the [German iPad setup and operations guide](IPAD_TERMINAL_SETUP.de.md) for local
TLS, pairing, Guided Access, MDM considerations, and device acceptance. Ordinary
HTTP access on the production host is not a substitute for trusted mobile HTTPS.

Terminal deletion does not erase the location and device evidence already
snapshotted in historical bookings. Plan access, legal basis, and retention for
that data before enabling location capture.

## Projects and reports

Team projects use employee assignments, service orders, lifecycle state, and
planned versus actual hours. Referenced projects/orders must be retained or
deactivated rather than deleted. Project activity reports and CSV exports can
be filtered by the supported period, employee, project, and order fields.

HR working-time reports show start/end, gross duration, breaks, net work, and
approval information independently of project assignment. Exact clock-in/out
locations are excluded by default; HR must explicitly include them in the table
and CSV export.

Solo customer CRUD, personal billable-timesheet filters, and personal policy
screens are not exposed as Team features in 2.0. Customer/project references and
booking billability survive a mode switch, but a shared Team customer/billing
workspace is future work. Neither mode generates invoices or imports coding-agent
usage records yet.

CSV exports contain personal working-time data. Review content, recipients, and
retention before sharing. Browser downloads and print/PDF handoffs must be
verified in the actual desktop browser or installed PWA; an HTTP response alone
does not prove a local file was saved.

## Operations and mode changes

Keep secrets private, enable TLS, restrict database access, back up both data and
attachments, and rehearse a restore. Use version-pinned release images and the
[upgrade procedure](../UPGRADING.md). Never remove persistent volumes or run a
demo reset as an upgrade/recovery step.

An administrator considering a return to one-person operation should follow
[Switching modes safely](OPERATING_MODES.md#switching-modes-safely). Other active
people, open timers, unresolved requests/time approvals, and active terminals
must be addressed before entering Solo. Historical records are retained, not
deleted to satisfy the checks.

OpenClockwork provides technical controls and configurable calculations. It
does not certify compliance with employment law, collective agreements, payroll,
or privacy obligations. Operators must validate their own rules and processes.
